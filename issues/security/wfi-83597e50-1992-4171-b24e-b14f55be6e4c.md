## Summary

WordPress core's `wp_ajax_sample_permalink()` and `wp_ajax_get_permalink()` AJAX handlers did not check `edit_post` against the post ID supplied in the request. An authenticated user with Contributor-level access or higher could therefore call these actions with another user's post ID and retrieve its slug and sample permalink. This works even when the target post is a draft or pending post they cannot otherwise edit. The fix ships in security releases across six maintained branches.

## Impact

- **Site owners / hosting & platform:** Update to the patched release for your branch. The exposure matters most on multi-author sites that allow Contributor or Author registrations. On those sites, unpublished post slugs can leak planned content, such as embargoed announcements or product names. Managed hosts should confirm that auto-updates have rolled the minor release out.
- **Plugin & theme developers:** No action is required for code that uses these core handlers. If you ship custom AJAX or REST endpoints that accept a post ID and return post data (slug, permalink, title), use this as a reminder to gate them with `current_user_can( 'edit_post', $post_id )`, not just a generic `edit_posts` check.
- **Severity:** Medium. Exploitation requires an authenticated account. Only the slug and sample permalink are disclosed, not post content.

## Technical details

Both affected handlers live in `wp-admin/includes/ajax-actions.php`:

- `wp_ajax_sample_permalink()` backs the `sample-permalink` action, which the classic editor uses to preview and edit the post slug.
- `wp_ajax_get_permalink()` backs the `get-permalink` action.

According to the advisory, neither handler verified that the current user had the `edit_post` capability for the specific post ID in the request. A Contributor, who holds `edit_posts` for their own content, could therefore pass an arbitrary post ID and receive the slug and sample permalink of other users' draft or pending posts.

The advisory does not include the patch diff. The expected pattern for the remediation is a per-object capability check before any output:

```php
$post_id = isset( $_POST['post_id'] ) ? (int) $_POST['post_id'] : 0;
if ( ! current_user_can( 'edit_post', $post_id ) ) {
	wp_die( -1 );
}
```

The advisory does not describe any hook, schema, or database changes.
