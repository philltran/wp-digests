# Custom User Registration Fields for WooCommerce <= 2.2.3 - Unauthenticated Privilege Escalation via 'afreg_select_user_role' Parameter in Store API Checkout

- **Source:** Wordfence Intelligence
- **Type:** Vulnerability
- **Published:** 2026-08-29
- **CVE:** [CVE-2026-15369](https://www.cve.org/CVERecord?id=CVE-2026-15369)
- **CVSS:** 9.8 (Critical)
- **CWE:** CWE-269: Improper Privilege Management
- **Affected:** Custom User Registration Fields for WooCommerce (plugin) <= 2.2.3
- **Patched in:** 2.2.4
- **Researchers:** 0xd4rk5id3

- **Usefulness:** 5/5

## Summary

Custom User Registration Fields for WooCommerce <= 2.2.3 lets unauthenticated visitors pick their own user role during WooCommerce Store API checkout. The plugin stores the submitted `afreg_select_user_role` value in order meta and later passes it to `WP_User::add_role()` without checking it against the admin-configured list of allowed roles. An attacker can submit `administrator` and become an admin. Version 2.2.4 fixes it.

## Impact

**Site owners**
- Sites running <= 2.2.3 with the "User Role Selection" setting enabled are exposed to unauthenticated full takeover (CVSS 9.8). Sites with the setting disabled are outside the described exploit condition.
- Update to 2.2.4 or later.
- If you ran a vulnerable version with role selection enabled, audit `wp_users`/`wp_usermeta` for unexpected administrator (or other privileged) accounts, particularly ones created via checkout, and review recent orders for unusual `afreg_select_user_role` meta values.

**Plugin & theme developers / agencies**
- Check client sites and any fleet inventories for this plugin and its version.
- If you disable role selection as a stopgap, do so only until the update is applied; the advisory does not describe this as a fix.

**Headless & REST consumers**
- The attack path is the public `/wc/store/v1/checkout` Store API route, so headless storefronts are as exposed as classic themes. Blocking this at the edge is not something the advisory describes.

## Technical details

Per the advisory (no diff or patch was provided, so the exact fix is not described here), the flaw is a two-step chain:

1. `af_reg_checkout_data_to_order_meta_data_block()` accepts an attacker-controlled `afreg_select_user_role` value from the unauthenticated `/wc/store/v1/checkout` request and persists it in order meta.
2. `af_reg_custom_order_processing_function()`, hooked to `woocommerce_thankyou`, reads that meta and passes it directly to `WP_User::add_role()`.

The value is never validated against the plugin's admin-configured allowed role list, so any role slug, including `administrator`, is accepted. The attacker creates an account during checkout with a modified JSON body specifying the desired role.

The exploit requires the plugin's "User Role Selection" setting to be enabled. Classified as CWE-269 (Improper Privilege Management).

The expected remediation pattern is an allowlist check of the submitted role against the configured roles before persisting or applying it, but the advisory does not confirm how 2.2.4 implements this.
