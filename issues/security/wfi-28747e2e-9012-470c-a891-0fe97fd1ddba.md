## Summary

WordPress core's XML-RPC `_insert_post()` handler allowed internal-only builtin post types — notably `customize_changeset` — to be written through the generic post API. Doing so skipped the Customizer's per-setting capability checks, so a user who can create changesets but lacks `edit_css` (which maps to `unfiltered_css`) could write changeset values, including Additional CSS. The fix is included in the listed security releases across the 6.6 through 7.1 branches.

## Impact

- **Site owners / hosting & platform:** Update core to a patched release on your branch. Exposure is highest where the Customizer and `edit_css` capabilities diverge:
  - **Multisite**, where `unfiltered_css` is restricted and non–super admins lack `edit_css`.
  - **Custom role setups** that grant changeset-related capabilities without `edit_css`.
- **Mitigation if you can't patch immediately:** Disabling XML-RPC removes this specific vector. For example, return `false` from the `xmlrpc_enabled` filter, or block `xmlrpc.php` at the edge.
- **Plugin & theme developers:** No API change is described in the advisory. If you build custom roles or capability maps, review which roles can create `customize_changeset` posts versus hold `edit_css`.
- **Headless & REST consumers:** The advisory names only the XML-RPC path.

## Technical details

**Vulnerable path:** `wp_xmlrpc_server::_insert_post()`, the shared handler behind the XML-RPC post-creation and post-editing methods.

**What went wrong:**
- The handler accepted internal-only builtin post types such as `customize_changeset` as writable targets.
- Changeset content is normally persisted through `WP_Customize_Manager`, which checks each setting's own capability. The Additional CSS setting requires `edit_css`.
- Writing the changeset post directly through the generic post API bypassed those per-setting checks. The caller only needed the capability to create or edit changeset posts.
- As a result, arbitrary changeset values, including custom CSS, could be written by a user who lacks `edit_css`.

The advisory does not detail the patch itself. It is implied to restrict internal builtin post types from the generic XML-RPC post API, but no diff is provided.
