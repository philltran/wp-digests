# TrueBooker <= 1.2.6 - Unauthenticated Authorization Bypass Through User-Controlled Key to Account Takeover to 'truebooker_wp_user_id' Parameter

- **Type:** Vulnerability

- **Affected:** TrueBooker – Appointment Booking and Scheduler System (plugin) <= 1.2.6
- **Patched in:** 1.2.7
- **Researchers:** Décio Brandão

- **Usefulness:** 5/5

## Summary

TrueBooker – Appointment Booking and Scheduler System exposes an `admin_user_create_cus` AJAX action that performs no authentication, capability, or nonce check before handing the request-supplied `truebooker_wp_user_id` value to `wp_update_user()`. Because the target user ID is entirely attacker-controlled, an unauthenticated request can rewrite the email address on any account on the site — administrators included. Once the email is changed, the attacker triggers WordPress's stock lost-password flow, receives the reset link at their own address, and takes over the account outright. Fixed in 1.2.6's successor, 1.2.7; anything at or below 1.2.6 is exploitable with a single unauthenticated POST.

## Impact

**Site owners running TrueBooker**
- Treat this as an active-exploitation-class issue: a full administrator takeover requires no account, no nonce, and no user interaction. Update to 1.2.7 immediately; if you cannot update in the next few minutes, deactivate the plugin.
- Post-update, assume compromise on any site that was internet-reachable while vulnerable. Audit `wp_users.user_email` for accounts whose address you do not recognise, check for unexpected administrator-role users, review recently installed plugins/themes and `wp_options` autoloaded entries, and force a password reset for all privileged accounts.

**Agencies & platform teams**
- Inventory fleets for the plugin slug and pin a minimum version of 1.2.7. Because the entry point is `admin-ajax.php`, WAF/edge rules blocking `action=admin_user_create_cus` from unauthenticated sources are a viable stopgap while updates roll out.
- Log review is worthwhile even on patched sites: `POST /wp-admin/admin-ajax.php` with that action from an unauthenticated session, followed shortly by a `wp-login.php?action=lostpassword` request, is the signature of the full chain.

**Plugin & theme developers**
- No action on your own code unless you bundle or depend on TrueBooker — but this is the canonical CWE-639 shape: an ID accepted from the request and used as the subject of a privileged write. Any handler that accepts a user ID, post ID, or booking ID from `$_POST` needs both a capability check and an ownership check tying that ID to the current user.

**Headless / REST consumers**
- Not affected directly; the vulnerable surface is `admin-ajax.php`, not a REST route. Account takeover of an admin account will, however, compromise any application password or JWT-style credential issued from that site.

## Technical details

The defect is in the plugin's `admin_user_create_cus` AJAX handler. Reaching it as an unauthenticated visitor means it is registered on the `wp_ajax_nopriv_` side (`add_action( 'wp_ajax_nopriv_admin_user_create_cus', ... )`) in addition to `wp_ajax_`, and the handler body contains no `is_user_logged_in()`, `current_user_can()`, or `check_ajax_referer()` gate. The `truebooker_wp_user_id` request parameter is passed straight through as the `ID` member of the array given to `wp_update_user()`, so the caller — not the plugin — chooses which account gets modified. `wp_update_user()` happily updates `user_email` for whatever existing ID it is handed; there is no capability check inside core's function, because core expects the caller to have done that.

The exploit chain is two steps and needs nothing but the target's user ID (`1` is a good first guess on most installs):

1. `POST /wp-admin/admin-ajax.php` with `action=admin_user_create_cus`, `truebooker_wp_user_id=1`, and an attacker-controlled email → the administrator's `user_email` is overwritten.
2. `POST /wp-login.php?action=lostpassword` for that administrator's username → WordPress mails the reset link to the attacker's address.

The missing guard, in the shape a correct handler needs:

```php
// Vulnerable (<= 1.2.6): no auth, no nonce, no ownership check.
function admin_user_create_cus() {
    $user_id = $_POST['truebooker_wp_user_id'];
    wp_update_user( array(
        'ID'         => $user_id,
        'user_email' => $_POST['email'],
    ) );
}

// Correct shape: authenticated, nonce-checked, and the ID is bound to
// the current user rather than taken from the request.
function admin_user_create_cus() {
    check_ajax_referer( 'truebooker_user_nonce', 'nonce' );
    if ( ! current_user_can( 'edit_users' ) ) {
        wp_send_json_error( null, 403 );
    }
    $user_id = absint( $_POST['truebooker_wp_user_id'] );
    if ( ! current_user_can( 'edit_user', $user_id ) ) {
        wp_send_json_error( null, 403 );
    }
    wp_update_user( array(
        'ID'         => $user_id,
        'user_email' => sanitize_email( wp_unslash( $_POST['email'] ) ),
    ) );
}
```

Note that sanitising or casting `truebooker_wp_user_id` is not the fix on its own — `absint()` still yields a valid, attacker-chosen ID. The authorization check (`current_user_can( 'edit_user', $user_id )`) is what closes CWE-639. No database schema, option, or hook changes are involved; the advisory records only that 1.2.7 remediates the handler.
