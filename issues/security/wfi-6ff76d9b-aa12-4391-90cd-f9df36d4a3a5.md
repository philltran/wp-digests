## Summary

`locate_template()` in WordPress core resolved a caller-supplied template name against the theme directories without checking that the resolved path stayed inside them. A template name containing `..` could therefore resolve to a readable `.php` file elsewhere on the server, and that file would then be included. The route an unauthenticated visitor can reach in core is `get_page_template()`, which builds `page-{$pagename}.php` from the URL-derived, url-decoded `pagename` query var. When the server also has a suitable PHP file such as `pearcmd.php` with `register_argc_argv=On`, this local file inclusion becomes remote code execution. The fix ships in point releases on every supported branch back to 4.7.

## Impact

**Site owners / hosting & platform**
- **Update core immediately** to the patched point release for your branch. This is unauthenticated and can lead to RCE.
- A site is exploitable only when both conditions below hold:
  1. The active parent **or child** theme has a **top-level directory whose name begins with `page-`**. Examples are `page-templates/` in Twenty Twelve, Twenty Fourteen, Neve, Hestia and Sydney.
  2. The web-server account can read a useful `.php` target outside the theme. The advisory's example is `pearcmd.php` with `register_argc_argv=On`, which is the default in the official PHP Docker image and in default cPanel setups on PHP < 8.5.
- Hosts should consider whether `register_argc_argv` needs to be on for web SAPIs, and whether PEAR is installed in the include path on web-facing PHP images. Treat this as defense in depth, not as a substitute for patching.

**Plugin & theme developers**
- The flaw sits in `locate_template()` itself, not only in the page-template path. Any code that passes request-derived input to `locate_template()`, `get_template_part()`-style helpers built on it, or `get_query_template()` was relying on a containment check that did not exist. Audit such call sites. On unpatched sites, sanitize the input yourself (for example, reject `..` and path separators).
- Theme authors: shipping a top-level directory named `page-*` is one of the exploitation preconditions. Patched core removes the vulnerability, but the naming explains why common themes were listed as affected.

**Headless & REST consumers**
- The advisory describes only the front-end template-resolution vector. It says nothing specific about REST.

## Technical details

**Vulnerable path (per the advisory):**

- `get_page_template()` adds `page-{$pagename}.php` to its candidate list. The `$pagename` comes from the `pagename` query var, which is derived from the request URL and url-decoded.
- The candidate list goes through `get_query_template()` to `locate_template()`.
- `locate_template()` checks each candidate against `STYLESHEETPATH`/`TEMPLATEPATH` (child, then parent) with `file_exists()`, then includes the first match.
- It never confirmed that the resolved path stayed within those theme roots.

**Why a `page-*` directory is required:** the candidate filename always starts with the literal `page-`. Traversal therefore only resolves when `page-<something>` is a real directory under the theme root. The path can then step out with `..` segments, as in this illustrative shape (not taken from the advisory):

```text
{theme}/page-templates/../../../../<path>/target.php
        ^^^^^^^^^^^^^^ must exist for the path to resolve
```

**RCE escalation:** the advisory gives `pearcmd.php` with `register_argc_argv=On` as the example target that turns inclusion into code execution.

**Fix:** the advisory says the flaw was the missing check that the resolved template stays inside the theme directories. The patch therefore closes that gap in `locate_template()`. The record contains no diff, so the exact implementation (canonicalization method, any new filter, and behavior for legitimate out-of-tree template paths) is not documented here. Check the release changeset before relying on specific semantics.
