## Summary

Hummingbird's page-cache debug log can be turned into a web-accessible PHP webshell by an anonymous visitor. The log file `wp-content/wphb-logs/page-caching-log.php` is meant to be protected by a leading `<?php die(); ?>` header, but a broken `class_exists( 'Filesystem' )` guard omits that header when the file is created during a front-end request. `get_cookies()` then writes raw `wphb_cache_*` cookie names into the file unsanitized, so a single request with a crafted cookie name plants PHP that runs when the file is requested directly. Fixed in 3.21.1.

## Impact

**Site owners**
- Update Hummingbird to 3.21.1 or later. The record rates this 9.8 (Critical) and unauthenticated.
- Exposure requires Page Caching with the **Debug Log** option enabled, which is non-default. Sites without it are not reachable through this path.
- Sites with the Debug Log enabled should turn it off until patched, and check `wp-content/wphb-logs/page-caching-log.php` for content that doesn't look like log lines, especially `<?php` blocks or a missing `die()` header. A compromised log file means the site should be treated as compromised.

**Hosting & platform teams**
- The vulnerable state can arise without admin interaction: the daily log-rotation cron can recreate the file from a front-end request context and strip the protective header from an existing log.
- Blocking direct web access to `wp-content/wphb-logs/` at the web server level is a reasonable defense-in-depth measure. It is not a substitute for patching.

**Plugin & theme developers**
- No API changes are described. The issue is a namespace-related logic error worth recognizing in your own code (see technical details).

## Technical details

Per the advisory, the flaw chains three problems in `core/modules/class-page-cache.php`:

1. **Broken header guard.** `log_msg()` only writes the `<?php die(); ?>` header when `class_exists( 'Filesystem' )` is true. `class_exists()` with a string argument resolves in the global namespace, but the class is `Hummingbird\Core\Filesystem`, so the check can never match. When the log is created during a front-end request, the header is omitted entirely.
2. **Unsanitized write.** `get_cookies()` writes the raw name of any cookie matching the `wphb_cache_` prefix into the log with no sanitization.
3. **Direct execution.** The log is a `.php` file under `wp-content/wphb-logs/`, reachable over HTTP. Requesting it executes any PHP injected via the cookie name.

Triggers for creating the log in a front-end context, per the advisory, are the plugin's own 'Clear logs' action, any cache flush, or the daily log-rotation cron, which can strip the header from an existing file.

This is classified as CWE-94 (code injection). The advisory doesn't describe the 3.21.1 patch itself, so the exact fix (correcting the namespaced class reference, sanitizing cookie names, or both) is not confirmed here.

```php
// Pattern that never matches inside a namespaced plugin:
if ( class_exists( 'Filesystem' ) ) { /* write die() header */ }

// The class actually lives at:
// Hummingbird\Core\Filesystem
// (use Filesystem::class or a fully qualified name)
```
