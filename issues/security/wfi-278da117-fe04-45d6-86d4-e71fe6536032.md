## Summary

WordPress core's login screen reflects the submitted `log` value (the username field on `wp-login.php`) back into authentication error messages without sufficient escaping, allowing an unauthenticated attacker to inject arbitrary JavaScript that executes in a victim's browser. Because the payload has to arrive with the login POST, exploitation requires tricking a visitor into submitting a crafted request — typically an auto-submitting form on an attacker-controlled page — which is why it scores 6.1 rather than higher. The fix hardens sanitization/escaping of the login error output. Notably, the vulnerable code reaches back to 4.7.0, so patched builds were shipped simultaneously for every branch from 4.7 through 7.0.

## Impact

**Site owners / operators**
- Any site running an affected branch is exposed. Confirm you are on a patched release; sites with background updates enabled for minor/security releases should already have received it, since WordPress ships security fixes to all old branches.
- Sites that pin core to an exact version (Composer-managed installs, `WP_AUTO_UPDATE_CORE => false`, image-baked cores) will **not** self-heal — bump the pin.
- No configuration change, DB migration, or content fix is required beyond updating.

**Plugin & theme developers**
- No public API changed and nothing is deprecated. Do not expect a code change in your plugin as a result of this advisory itself.
- However, if you render a **custom login form or custom login error output** — anything hooking `login_errors`, `wp_login_errors`, `authenticate`, or a front-end login template that echoes `$_POST['log']` / `$_REQUEST['log']` back to the page — audit that path. Core's patch does not protect markup you emit yourself.
- The same applies to error strings you build with the submitted username interpolated in ("Unknown username: %s"). Escape at output, every time.

**Hosting & platform teams**
- Worth a fleet-wide core-version audit; the affected range is effectively "every WordPress since December 2016," so version-based triage is more useful than exploit-signature triage.
- A WAF rule on `log` POST values containing markup is a reasonable stopgap for customers who cannot update immediately, but it is not a substitute for the core update.

**Headless / REST consumers**
- Not directly affected: this is `wp-login.php` screen rendering, not a REST route. Decoupled front ends that implement their own login UI against a custom auth endpoint must do their own escaping of any username echoed into an error state.

## Technical details

The advisory attributes the flaw to "insufficient input sanitization and output escaping of the authentication error messages rendered on the login screen." `log` is the name of the username input on `wp-login.php`; on a failed sign-in the submitted value flows into the `WP_Error` messages rendered above the form, and an attacker-supplied value could break out of that context and execute script.

Wordfence does not publish the specific file, function, or changeset, so the exact escaping call added upstream is not stated in the record — treat the mechanism above as the attack path, not as a line-level description of the patch.

The delivery constraint matters for triage: because `log` is submitted with the login request rather than sitting in a bookmarkable URL, exploitation is the "specially crafted, attacker-controlled page that submits a request to the vulnerable site" pattern — an auto-submitting cross-site form. That means it fires in the context of whoever visits the attacker's page, not only logged-in admins, and `login_form` nonce checks do not stand in the way of a failed-login error render.

For custom login surfaces, the defensive pattern is unchanged and worth re-checking:

```php
// Vulnerable: attacker-controlled value straight into markup
$user = $_POST['log'];
$errors->add( 'invalid_username', sprintf( 'Unknown username: %s', $user ) );

// Safe: escape at the point of output, in the right context
$user = isset( $_POST['log'] ) ? wp_unslash( $_POST['log'] ) : '';
$errors->add(
	'invalid_username',
	sprintf( 'Unknown username: %s', esc_html( $user ) )
);
```

No hooks, filters, options, REST schema, or database structures are added or altered by this fix.
