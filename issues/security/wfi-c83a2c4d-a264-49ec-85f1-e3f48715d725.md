## Summary

WordPress core does not sufficiently sanitize user-supplied CSS in post content, allowing an authenticated user with Author-level capabilities or above to inject arbitrary CSS that is then rendered to other visitors on the front end. Because the injected rules are served as part of the post output, an attacker can restyle or visually rewrite pages for readers — overlaying, hiding, or replacing content that the author would not otherwise be permitted to control. The fix tightens sanitization of user-supplied CSS and has been backported across every supported (and long-tail) branch from the 4.7 line forward. This is a privilege-boundary issue, not a remote/unauthenticated one: it matters on any site where Author is not a fully trusted role.

## Impact

**Site owners**
- Update core. If you run automatic background updates for minor releases, the patched release will (or already did) land on its own; verify with `wp core version` rather than assuming.
- The practical exposure is proportional to how many Author+ accounts exist and how much you trust them. Multi-author publications, membership/community sites, and sites where contributors are promoted to Author by default carry the most risk; a single-admin brochure site effectively carries none.

**Plugin & theme developers**
- No API was removed or deprecated in this advisory, and no code change is required in plugins or themes.
- If your plugin accepts CSS from users and stores or echoes it (custom "additional CSS" fields, block/style panels, page-builder style boxes, shortcode `style` attributes), audit that path independently — a core fix does not cover your own sanitization gap. Route user CSS through `safecss_filter_attr()` / `wp_kses` style filtering rather than trusting it, and do not widen `safe_style_css` or `wp_kses_allowed_html` beyond what you actually need.

**Hosting & platform teams**
- The backport spans every branch back to 4.7, so fleet-wide patching is straightforward but broad: any site you host on any of those lines needs the corresponding patch release, not just sites on the current branch.
- Sites pinned to an old major for compatibility reasons still have a patched release available on their own line — pinning is not a reason to skip this one.

**Headless & REST consumers**
- Rendered post content delivered through `/wp/v2/posts` (`content.rendered`) reflects the same sanitization layer. A decoupled front end that injects `content.rendered` into the DOM inherits the injected CSS, and client-side sanitizers that strip `<script>` but permit `style` attributes or `<style>` blocks will not stop it. Patch core and confirm your front-end sanitizer's allow-list.

## Technical details

The advisory classifies this as CWE-74 (improper neutralization of special elements in output used by a downstream component) with a CVSS of 5.5, and attributes the root cause to insufficient sanitization of user-supplied CSS that is subsequently emitted in post output. Wordfence's record does not name the specific function, file, or CSS property involved, and no proof-of-concept or patch diff is published alongside it, so the precise sanitization gap is not identifiable from this record alone.

What the classification does tell you: the payload survives core's escaping layer and reaches the rendering context intact, and the trust boundary crossed is capability-based — `edit_posts` plus `publish_posts` (Author) is enough, so this is not restricted to Editors or Administrators who could already inject markup via `unfiltered_html`. Note that on multisite, `unfiltered_html` is stripped from everyone except Super Admins, which makes the CSS sanitization layer the *only* thing standing between an Author and the front-end render — multisite installs should treat this as the higher-exposure configuration.

CSS injection is materially weaker than stored XSS (no script execution, no session theft via `document.cookie`), but it is not cosmetic: attribute selectors combined with `background-image: url(...)` can exfiltrate rendered page data to a third-party host, and absolute-positioned overlays can spoof UI or conceal content for readers and reviewers. Grade it as a content-integrity and phishing-surface issue rather than a code-execution one.

No new hooks, filters, options, REST schema fields, or database changes are described. Upgrading is the entire remediation.

## Contribution

The Wordfence record carries no discussion detail, patch reference, or researcher credit — only the affected-version matrix and the corresponding patched releases.
