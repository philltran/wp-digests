## Summary

WordPress core did not sufficiently escape user display names when rendering the Quick Edit (inline edit) UI on admin list tables, allowing a user who controls their own display name — Contributor role and above — to store markup that executes in the browser of any higher-privileged user who opens the affected list screen. Because a display name is persisted on the user record and re-rendered on every load of the screen, this is a stored (persistent) XSS in the wp-admin origin, not a reflected one. Wordfence notes the issue only manifests on sites with a large number of users, so the vulnerable rendering path is the alternate author-field markup core emits once a site crosses its large-user-count threshold rather than the ordinary author `<select>`. The fix is output escaping, shipped as a coordinated security release across every supported branch back to 4.7.

## Impact

**Site owners / multi-author sites**
- Anyone running an untrusted or open-registration site that grants Contributor (or higher) accounts, *and* has a large user base, should confirm the security release actually applied. Core background updates for minor security releases cover this by default, but sites with `WP_AUTO_UPDATE_CORE` disabled, `AUTOMATIC_UPDATER_DISABLED` set, or a read-only/immutable filesystem deployment will not have picked it up.
- Practical exposure is narrow: the attacker needs an account whose display name they can edit (the profile screen lets any role set nickname/display name), and a privileged user must then open the list table containing that author.
- No configuration change, data migration, or content cleanup is required beyond updating — though on a site you suspect was targeted, auditing `wp_users.display_name` and the `nickname`/`first_name`/`last_name` user meta for markup is a cheap check.

**Plugin & theme developers**
- No API was removed or deprecated; nothing in your code needs to change to be compatible with the fix.
- Do audit your own admin output for the same class of bug: any custom list-table column, custom Quick Edit field, author picker, or admin notice that echoes `$user->display_name`, `get_the_author_meta( 'display_name' )`, or `get_userdata()->display_name` without `esc_html()` / `esc_attr()` remains vulnerable regardless of the core patch. The same applies to display names passed into JS via `wp_localize_script()` / `wp_add_inline_script()` without `wp_json_encode()`.

**Hosting & platform teams**
- Twenty-four branches received a patched release. If you manage a fleet pinned to older majors, map each site's branch to its corresponding patch version rather than assuming a single target — several long-EOL-adjacent branches (4.7.x–5.x) are included.
- Worth a one-off fleet query for sites that are both large-user-count and permit self-registration at Contributor or above; those are the ones where the precondition is genuinely met.

**Headless & REST consumers**
- Not affected. `display_name` handling in the REST users controller is unchanged, and no schema or route changed. If your own front end renders user display names into HTML, escape at that boundary as usual.

## Technical details

The attack chain is the classic self-set-identity stored XSS:

1. A Contributor-level (or higher) account sets a display name containing HTML/JS payload — display name is user-settable from `profile.php`, derived from the nickname/first/last fields, so no elevated capability is needed to plant it.
2. An Editor or Administrator loads an admin list table (`edit.php` and friends) where the Quick Edit row is emitted inline with the post rows.
3. The display name is written into that markup without adequate escaping, and the payload runs with the privileged user's session in the wp-admin origin — the standard path to a rogue administrator account or a persisted backdoor.

The "large number of users" precondition is the interesting part: on ordinary sites the Quick Edit author field is a fully-escaped `wp_dropdown_users()` `<select>`, and it is only past core's large-user-count threshold — where core stops enumerating every user and swaps in a different author control — that the unescaped rendering is reached. That is why the bug survived so long across so many branches. Wordfence does not publish the patched file or the diff, so the exact sink is not stated in the record; do not assume it from this description.

For your own code, the pattern to look for and the fix are the usual ones — escape late, at the point of output, choosing the escaper for the context:

```php
// Vulnerable: display_name is attacker-controlled text.
echo '<option value="' . $user->ID . '">' . $user->display_name . '</option>';
printf( '<span class="author">%s</span>', $user->display_name );

// Correct: context-appropriate escaping.
printf(
    '<option value="%d">%s</option>',
    (int) $user->ID,
    esc_html( $user->display_name )
);
printf( '<span class="author">%s</span>', esc_html( $user->display_name ) );

// For values crossing into JS:
wp_add_inline_script( 'my-admin', 'window.myAuthor = ' . wp_json_encode( $user->display_name ) . ';' );
```

No hooks, filters, options, capabilities, `block.json` fields, REST schema, or database structures changed. This is an escaping-only fix with no behavioral surface for third-party code to adapt to.
