# WordPress Core <= 7.1 - Authenticated (Contributor+) Path Traversal via REST Templates Controller

- **Usefulness:** 5/5

## Summary

WordPress core has a path traversal bug in `_get_block_template_file()`, the function the REST templates controller uses to resolve a template slug into a file path. The slug is turned into a path without checking that it stays inside the theme's template directory. The route regex blocks `.`, but the sanitize callback URL-decodes the value twice, so a double-encoded `../` sequence passes the regex and reaches file resolution. As a result, any authenticated user with Contributor-level access or higher can read arbitrary `.html` files outside the theme template directory through `/wp/v2/templates/<id>?source=theme`.

## Impact

- **Site owners:** Update to the patched minor release for your branch. Exposure depends on who holds Contributor-level (or higher) accounts, so sites with open registration elevated to Contributor, multi-author newsrooms, and membership or LMS setups that hand out Contributor+ roles face the most risk. The flaw only allows **reading** `.html` files. The advisory does not describe write access or code execution.
- **Hosting & platform teams:** Every branch from 5.8 onward is affected, and each has a patched minor. Confirm that minor or security auto-updates are actually landing on managed fleets, especially sites pinned to older branches.
- **Plugin & theme developers:** The advisory describes no public API change. Code that builds file paths from template or template-part slugs, or that runs decoding steps after route-level validation, should be checked for the same double-decode pattern.
- **Headless & REST consumers:** The vulnerable surface is the `wp/v2/templates` route with `source=theme`. Legitimate slug lookups should not be affected. The advisory does not describe the patch's behavior, so verify against your own integration after updating.
- **Interim mitigation (not from the advisory):** If you cannot update immediately, a WAF rule that rejects double-encoded dot or slash sequences (e.g. `%252e`, `%252f`) in `/wp/v2/templates/` request paths targets the described vector.

## Technical details

The advisory identifies these parts of the flaw:

- **Sink:** `_get_block_template_file()` resolves a template slug to a file path with no directory containment check.
- **Entry point:** the REST templates controller route `/wp/v2/templates/<id>`, queried with `?source=theme`.
- **Bypass:** the route's `<id>` regex rejects `.`. The route's sanitize callback then URL-decodes the value **twice**. A double-encoded traversal sequence therefore contains no literal `.` during regex validation, and it becomes a real `../` only after sanitization, when it reaches `_get_block_template_file()`.
- **Scope:** only files ending in `.html` can be read, since template files are resolved with that extension. The files can sit anywhere the traversal reaches outside the theme's template directory.
- **Required privilege:** Contributor and above.

Illustrative encoding chain, derived from the advisory's description:

```text
%252e%252e%252f  --(passes route regex: no literal '.')-->
%2e%2e%2f        --(1st urldecode in sanitize callback)-->
../              --(2nd urldecode) --> path traversal in _get_block_template_file()
```

The advisory does not say how the patch works, for example whether it adds containment via realpath comparison, removes the second decode, or tightens slug validation.
