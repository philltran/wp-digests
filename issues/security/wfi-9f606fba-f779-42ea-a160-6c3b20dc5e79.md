# User Profile Builder <= 3.16.4 - Unauthenticated Authentication Bypass via Type Confusion to Administrator Account Takeover via 'username' Parameter

- **Type:** Vulnerability
- **Published:** 2026-08-14
- **CVE:** [CVE-2026-15826](https://www.cve.org/CVERecord?id=CVE-2026-15826)
- **CVSS:** 9.8 (Critical)
- **CWE:** CWE-704: Incorrect Type Conversion or Cast
- **Affected:** User Profile Builder – Beautiful User Registration Forms, User Profiles & User Role Editor (plugin) <= 3.16.4
- **Patched in:** 3.16.5
- **Researchers:** Supakiad S. (m3ez)
- **Link:** [https://www.wordfence.com/threat-intel/vulnerabilities/id/9f606fba-f779-42ea-a160-6c3b20dc5e79](https://www.wordfence.com/threat-intel/vulnerabilities/id/9f606fba-f779-42ea-a160-6c3b20dc5e79)
- **Usefulness:** 5/5

## Summary

User Profile Builder's registration flow calls `absint()` on the return value of `wp_insert_user()` *before* testing it with `is_wp_error()`. When core rejects a registration — specifically for a username of 61–70 characters — it returns a `WP_Error` object, but `absint()` has already coerced that object to the integer `1`, so the `is_wp_error()` guard never fires and execution continues as if user ID 1 had just been created. The plugin then issues its transient-backed autologin nonce bound to user ID 1, letting an unauthenticated visitor log in as the site's administrator. Fixed in 3.16.5; anything up to and including 3.16.4 is exploitable with a single crafted registration submission and no authentication.

## Impact

**Site owners running User Profile Builder**
- Any site on <= 3.16.4 with a reachable UPB registration form should be treated as remotely takeover-able by an unauthenticated visitor. Update to 3.16.5 immediately; this is not a "schedule it for the next maintenance window" fix.
- The bypass is hard-bound to **user ID 1**, so the practical blast radius depends on what that account is on your install — on the overwhelming majority of sites it is the original administrator.
- Because exploitation produces a *legitimate* login for user 1, post-update triage matters: review recent successful logins for user ID 1, newly created administrator or editor accounts, changed admin email/password, modified `users_can_register`/`default_role` options, and any plugin/theme files written since the plugin was last known-good. Rotate the admin password and force a global session logout (`wp_destroy_all_sessions()`) — an issued autologin session survives the plugin update.
- Clearing the plugin's autologin transients is worthwhile if you suspect exploitation, since the nonce is transient-backed.

**Hosting and platform teams**
- Worth a fleet-wide inventory of the plugin slug and a forced update; the pre-auth, no-user-interaction, CVSS 9.8 profile is the class that gets mass-scanned within days of disclosure.
- A WAF/edge rule rejecting registration POSTs with a `username` parameter longer than 60 bytes is a reasonable stopgap for sites that cannot be updated in the same window.

**Plugin and theme developers**
- No API change to react to, but the bug class is worth internalising: `absint()`, `intval()`, and `(int)` all cast a `WP_Error` object to `1` rather than failing, so any `is_wp_error()` check placed *after* a numeric coercion is dead code. Audit your own `wp_insert_user()`, `wp_insert_post()`, `wp_insert_term()`, and `wp_update_user()` call sites for the same ordering — a coerced `wp_insert_post()` failure silently aliases to post ID 1 in exactly the same way.

**No action required** for sites that do not have User Profile Builder installed.

## Technical details

The defect is in `wppb_log_in_user()`. The plugin takes the result of `wp_insert_user()` and normalises it with `absint()` in the same expression, then applies the error guard to the already-normalised value:

```php
// Vulnerable ordering (<= 3.16.4)
$user_id = absint( wp_insert_user( $userdata ) );

if ( is_wp_error( $user_id ) ) {
    // unreachable: $user_id is an int by this point
    return $user_id;
}

// proceeds to bind an autologin nonce to $user_id
```

PHP casts an object to `int` as `1`, so a failed insert does not yield `0` or `false` — it yields the ID of the first user on the site. The guard evaluates `is_wp_error( 1 )`, which is `false`, and execution falls through into the success path.

The trigger is a username of **61–70 characters**. Core's user validation rejects it and `wp_insert_user()` returns a `WP_Error` instead of an ID, which is precisely the condition the coercion swallows. The plugin then generates and stores its transient-backed autologin nonce against user ID 1 and returns it to the unauthenticated requester, who redeems it for an administrator session.

The correct ordering — check first, coerce second — is what the fix requires:

```php
// Correct ordering
$user_id = wp_insert_user( $userdata );

if ( is_wp_error( $user_id ) ) {
    return $user_id;   // fires as intended
}

$user_id = absint( $user_id );
```

No database schema, hook, or option changes are involved; the entire vulnerability is the evaluation order of two lines in the registration handler. Note that the autologin nonce is stored in a transient, so a session issued during the exploitable window persists across the plugin update until transients are flushed and sessions destroyed.
