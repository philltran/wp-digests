## Summary

The ERP: Complete HR, Accounting & CRM Suite Built for WooCommerce plugin (<= 1.17.8) writes inbound IMAP email attachments to disk in `save_attachments()` without validating the file extension or normalizing the filename. An unauthenticated attacker can email the site's configured inbound mailbox with an attachment named like `../helper.php`, and the cron-driven IMAP sync will write that PHP file outside the protected `crm-attachments` directory and into `wp-content/uploads/`. Version 1.17.9 fixes it.

## Impact

**Site owners**
- Affected only if the CRM module and the IMAP Email Connect feature are both enabled and configured. Sites without that setup are not exposed through this path.
- Update to 1.17.9 or later.
- Where PHP executes from `wp-content/uploads/`, a successful upload leads to remote code execution. Where it does not, the file is written but not directly executable.
- If you ran an affected version with IMAP Email Connect active, check `wp-content/uploads/` (and parent-relative locations) for unexpected `.php` files and review the inbound mailbox for suspicious messages with odd attachment names.

**Hosting & platform teams**
- Denying PHP execution in `wp-content/uploads/` (web server config) blunts the RCE outcome for this class of bug, though it does not stop the file write.

**Plugin & theme developers**
- No API changes are documented. The relevant lesson is that attachment filenames from external mail are attacker-controlled.

## Technical details

The vulnerable function is `save_attachments()`, which handles attachments during CRM Email Connect's cron-based IMAP sync. Per the advisory, two checks were missing:

- **File extension validation:** dangerous types such as `.php` were not rejected.
- **Path normalization:** an attachment filename containing traversal sequences (e.g. `../helper.php`) was used as-is, so the write escaped the `.htaccess`-protected `crm-attachments` directory and landed in `wp-content/uploads/`.

The attacker must also send a forged `References` header matching the pattern the plugin expects, which is how the crafted message gets processed as a legitimate reply. The advisory does not describe the exact code of the 1.17.9 patch, so the specific validation added is not stated here.

The issue is classed as CWE-434 with a CVSS of 9.8, reflecting the unauthenticated network vector.
