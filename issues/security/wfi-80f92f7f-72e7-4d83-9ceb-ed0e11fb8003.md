## Summary

WordPress multisite honors a network-wide signup policy (the `registration` site option: `none`, `user`, `blog`, or `all`), but the `gimmeanotherblog` signup stage in `wp-signup.php` did not verify that policy before processing the request. On a network configured to allow user registration only (`registration` = `user`), any logged-in user at Subscriber level or above could POST the `gimmeanotherblog` stage and create a new site anyway, bypassing the network admin's intent. The fix adds the missing active-signup check to that code path. Single-site installs are not affected in any way; only multisite networks are.

## Impact

**Multisite network operators / hosting & platform teams**
- Affected only if the install is multisite. Networks with **Allow new registrations** set to *User accounts may be registered* (`registration` = `user`) are the exploitable configuration — user signup is on, site signup is meant to be off, and that boundary was not enforced.
- Networks set to `none` (registration disabled) or to `blog`/`all` (site creation already permitted) do not gain unauthorized site creation from this issue.
- Practical effect is unauthorized site sprawl on the network: spam/SEO subsites, consumption of per-user site quotas, storage and backup growth, and extra tenants in any per-site provisioning or billing automation.
- **Action:** update to the patched release on your branch. Core's automatic background updates will deliver this to most installs; managed hosts pinning core versions, or networks with `WP_AUTO_UPDATE_CORE` disabled/constrained, need to schedule the update explicitly.
- After patching, audit for sites created while exposed — e.g. `wp site list --field=url --fields=blog_id,url,registered` sorted by registration date — and review the `wp_signups` table for completed signups that predate the fix.

**Plugin & theme developers**
- No API change, no deprecation, no signature change. Code that filters `wpmu_active_signup` to relax or tighten signup policy behaves the same, but that filter's return value is now actually respected on the `gimmeanotherblog` path.
- **Site owners on single-site WordPress:** no action required.

## Technical details

The signup flow in `wp-signup.php` dispatches on a `stage` value posted by the form: `gimmeanotherblog` is the stage used by an already-logged-in user requesting an additional site (rendered by `signup_another_blog()`, processed by `validate_another_blog_signup()`), as distinct from the logged-out `validate-user-signup` / `validate-blog-signup` stages.

That dispatch is supposed to be gated by the network's effective signup policy:

```php
$active_signup = get_site_option( 'registration', 'none' );
/** Filters the type of site sign-up. */
$active_signup = apply_filters( 'wpmu_active_signup', $active_signup );
// 'none' | 'user' | 'blog' | 'all'
```

Per the advisory, the `gimmeanotherblog` branch ran without consulting `$active_signup`, so a request reached the site-creation path even when the resolved policy was `user` — i.e. accounts may register, but sites may not. Because the only other requirement is being authenticated, the privilege bar is Subscriber (no `create_sites`-style capability or network-admin role is involved), which is what makes this a CWE-862 missing-authorization issue rather than a CSRF or capability-escalation one.

Behavior after the fix:

- `registration` = `none` → signup pages remain closed (unchanged)
- `registration` = `user` → `gimmeanotherblog` is now rejected instead of provisioning a site (**changed**)
- `registration` = `blog` / `all` → additional-site signup continues to work (unchanged)

No hooks, options, database schema, or REST routes are added or altered; the change is a policy check on an existing request path. Note that `wpmu_active_signup` is evaluated as part of that policy, so a plugin returning `all` from that filter still opens the path deliberately.
