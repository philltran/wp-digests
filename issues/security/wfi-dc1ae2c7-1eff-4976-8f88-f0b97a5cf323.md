## Summary

WordPress core's `wp_ajax_activate_plugin()` AJAX handler did not check the `manage_network_plugins` capability when activating a network-only plugin. On Multisite, a **site administrator** could therefore network-activate an installed plugin marked `Network: true`, which normally requires a Super Admin. Two causes combined to allow this: the missing capability check, and a path-normalization mismatch between `is_network_only_plugin()` and `activate_plugin()`. Security releases across the supported branches add the check.

## Impact

- **Multisite network operators / hosting & platform teams:** Update to the patched release for your branch. Exposure requires a site-administrator account on a subsite, so the risk is highest on networks that hand site-admin roles to untrusted or semi-trusted users, such as SaaS-style or university networks.
- **Scope limits:**
  - The attacker can only activate plugins that are already installed and network-only.
  - The flaw does not let anyone install or upload a plugin.
  - Single-site installs are not affected by the network-activation path described.
- **Plugin developers:** If you ship a network-only plugin, it may have been network-activated without a Super Admin's intent on unpatched networks. Consider whether activation hooks that assume Super Admin context could be abused, for example setup routines that write network-wide options.
- **Everyone else:** No code changes are required beyond applying the core update. Auto-updates for minor or security releases will deliver the fix.

## Technical details

- **Entry point:** the `wp_ajax_activate_plugin()` AJAX action.
- **Flaw 1, missing capability check:** When the target was a network-only plugin, the handler did not require `manage_network_plugins`. The capability a site admin holds was enough to reach network activation.
- **Flaw 2, path mismatch:** `is_network_only_plugin()` and `activate_plugin()` normalized the plugin path differently. The network-only detection could therefore be evaluated against a different path than the one actually activated, letting the request bypass logic that would otherwise force network-level handling.
- **The fix:** Per the advisory, the patched releases add the `manage_network_plugins` check for network-only plugins in this AJAX path and resolve the normalization mismatch.
- **What the advisory does not include:** the exact diff, the changesets, and any new filters. No new hooks or APIs are indicated.
- **Auditing a network:** Review `get_site_option( 'active_sitewide_plugins' )` for network-only plugins that a Super Admin did not intentionally activate.
