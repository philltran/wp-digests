# MStore API <= 4.20.0 - Unauthenticated Authentication Bypass via 'id_token' Parameter JWT Forgery

## Summary

The MStore API plugin's Firebase Phone Auth login path did not verify the JWT signature on the `id_token` it received. `FirebasePhoneAuthHelper::verify_id_token()` checked the claims (`alg`, `kid`, `aud`, `iss`) but never validated the signature against Google's public certificates. An unauthenticated attacker can therefore forge a token signed with their own RSA key pair, impersonate any phone number, and log in as an existing user or create a new account. Version 4.21.1 is the patched release.

## Impact

**Site owners**
- Any site running MStore API <= 4.20.0 is exposed to unauthenticated account takeover and arbitrary account creation (CVSS 9.8). Update to 4.21.1 or later.
- If the plugin was installed while vulnerable, review users for unexpected accounts, especially recently created ones and any privileged accounts tied to a phone number. Also check for suspicious logins. The advisory does not describe indicators of compromise, so this is a precaution.
- If you cannot update immediately, deactivating the plugin removes the exposure. The advisory does not describe a configuration-based mitigation.

**Plugin & theme developers / agencies**
- Audit fleets for MStore API installs, including mobile-app backends that may not be checked routinely.
- No API changes are documented. This is a security fix with no migration steps beyond updating.

**Hosting & platform teams**
- Consider WAF or virtual-patching rules for requests carrying the `id_token` parameter to the plugin's phone-auth endpoints until sites are updated. The advisory does not name the exact route.

## Technical details

The flaw is in `FirebasePhoneAuthHelper::verify_id_token()`. Per the advisory, it decodes the Firebase ID token and validates the claims `alg`, `kid`, `aud` and `iss`, but never calls `openssl_verify()` or any equivalent to check the JWT signature against Google's published public key certificates.

Because only the claims are checked, an attacker can:

1. Generate their own RSA key pair.
2. Build a JWT whose claims satisfy the checks, including a chosen phone number.
3. Sign it with the self-generated private key.
4. Submit it as the `id_token` parameter.

The plugin then treats the phone number as verified. The result is authentication as an existing WordPress account or creation of a new arbitrary one.

The patched code in 4.21.1 is not included in the record, so the exact fix is not described here. The expected remediation is signature verification against Google's certificates, but that is not confirmed by the source.
