# SignUp & SignIn <= 1.0.0 - Unauthenticated Privilege Escalation via Weak Password Reset Validation via 'reset_activation_code' Leading to Account Takeover

## Summary

The SignUp & SignIn plugin (≤1.0.0) contains an unauthenticated privilege escalation vulnerability that allows attackers to reset any user’s password, including administrators, without triggering a legitimate password-reset flow. The flaw stems from the `pravel_change_password()` AJAX handler bypassing nonce verification and capability checks, while relying on a loose equality comparison against the `forgot_email` user meta. Because the meta field defaults to an empty string for users who have never requested a reset, an attacker can supply an empty or omitted `reset_activation_code` to bypass validation entirely. This enables direct account takeover via a single crafted `admin-ajax.php` request.

## Impact

- **Plugin users (≤1.0.0)**: Sites running this plugin are immediately vulnerable to unauthenticated account takeover. No patch has been released yet.
- **Site owners & administrators**: Must disable or uninstall the plugin immediately, or apply a temporary mitigation by restricting `admin-ajax.php` access or removing the vulnerable AJAX action.
- **Plugin & theme developers**: If you are building similar authentication flows, ensure password-reset endpoints enforce nonces, verify user capabilities, and use strict equality (`===`) or cryptographic token validation instead of comparing raw meta values.
- **Hosting & platform teams**: Monitor for POST requests to `admin-ajax.php` containing `action=pravel_change_password` and block or alert on them.

## Technical details

The vulnerability resides in the `pravel_change_password()` function, which is exposed to unauthenticated users via the `wp_ajax_nopriv_pravel_change_password` hook. The handler accepts `reset_user_id` and `new_password_custom` from the POST payload and validates the reset request by comparing the attacker-supplied `reset_activation_code` against the target user’s `forgot_email` meta value using a loose equality operator. When `get_user_meta()` returns an empty string (the default for accounts that never initiated a reset), the check passes trivially. The handler then overwrites the target account's credentials using the attacker-supplied `new_password_custom` value. A secure implementation would require a valid nonce, a capability check, and a cryptographically secure, time-limited token stored in a dedicated meta key, validated with `===` before invoking the password update.
