## Summary

WordPress core leaks the contents of internal notes through its public comment feeds. The comment feed output was built without excluding note-type entries, so anything written as an internal note on a post was serialized into the RSS/Atom comment feed alongside ordinary approved comments — readable by anyone, with no authentication and no interaction from a privileged user. The fix, shipped as a coordinated security release across every maintained branch, restricts comment feed output so internal notes are no longer included. Sites that never used internal notes have nothing to disclose, but the vulnerable code path is present in every listed version.

## Impact

- **Site owners / editorial teams:** If your workflow uses internal notes on posts, treat their contents as having been publicly readable. Editorial notes routinely contain embargo dates, legal or HR context, unpublished names, client feedback, and internal URLs — review what was written before assuming the exposure is harmless. Update to a patched release; minor-release auto-updates cover most sites automatically, but confirm rather than assume.
- **Plugin & theme developers:** No API was removed or renamed and no code change is required. If your plugin writes non-public comment records (notes, workflow annotations, moderation metadata) as comments, verify independently that your records are excluded from feed output — the fix addresses core's own note type, not arbitrary custom comment types you register.
- **Hosting & platform teams:** This is a cross-branch core security release covering every branch back to 4.7, so it touches essentially your entire WordPress fleet regardless of how old the sites are. Roll it out fleet-wide and verify version pinning didn't block it. **Purge cached feed responses after updating** — full-page caches, CDNs, and reverse proxies will happily keep serving a pre-patch `/comments/feed/` body containing note content long after the core files are replaced.
- **Headless & REST consumers:** Unaffected as a consumer — this is a feed-rendering issue, not a REST schema change. No client changes needed.
- **If you cannot patch immediately:** block or 404 the comment feed endpoints at the edge (`/comments/feed/`, `/?feed=comments-rss2`, `/?feed=atom&withcomments=1`, and per-post `<permalink>feed/`) until the update lands.

## Technical details

Per the advisory, the defect is insufficient restriction on which comment records reach feed output: internal notes are not excluded when the comment feed is generated, so they are rendered as feed items like any other approved comment. The exposed surface is the standard comment feed endpoints — the site-wide comment feed (`/comments/feed/`, `?feed=comments-rss2`) and per-post comment feeds — rendered by the `wp-includes/feed-rss2-comments.php` and `wp-includes/feed-atom-comments.php` templates. Because feeds are served to anonymous requests by design, no capability check stands between the attacker and the note body; CVSS 5.3 with no privileges and no user interaction reflects exactly that.

Wordfence's record does not publish the patch diff, so the precise filtering mechanism in the fix is not stated here — only that note entries are now excluded from feed output.

To check a site quickly:

```bash
# Anonymous request — inspect for note text that should not be public
curl -s 'https://example.com/comments/feed/' | grep -i -A3 '<item>'

# Per-post comment feed
curl -s 'https://example.com/some-post/feed/'
```

No hooks, filters, `block.json` fields, REST schema, or database structures change as part of this; the remediation is entirely a version bump.
