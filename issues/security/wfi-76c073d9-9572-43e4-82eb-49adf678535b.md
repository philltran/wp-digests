# Mail Mint <= 1.31.0 - Unauthenticated PHP Object Injection in Arbitrary Form Fields

- **Source:** Wordfence Intelligence
- **Type:** Vulnerability

- **CVE:** [CVE-2026-10196](https://www.cve.org/CVERecord?id=CVE-2026-10196)
- **CVSS:** 9.8 (Critical)
- **CWE:** CWE-502: Deserialization of Untrusted Data
- **Affected:** Mail Mint – Email Marketing, Automation & WooCommerce Emails with AI Assistance (plugin) <= 1.31.0
- **Patched in:** 1.31.1
- **Researchers:** maru

- **Usefulness:** 5/5

## Summary

The Mail Mint plugin passes untrusted form-submission input to PHP deserialization in its `handle_form_submission` function, allowing unauthenticated attackers to inject arbitrary PHP objects. Because a POP chain is present, this escalates to remote code execution on the server. Version 1.31.1 contains the fix. An earlier, incomplete patch shipped in 1.23.1.

## Impact

**Site owners**
- Any site running Mail Mint <= 1.31.0 is exposed to unauthenticated remote code execution (CVSS 9.8). Update to 1.31.1 or later immediately.
- The advisory says 1.23.1 only partially patched the issue, so sites that updated to a version between 1.23.1 and 1.31.0 are still vulnerable.
- If you cannot update right away, deactivate the plugin, since the vulnerable path is reachable without authentication.
- The record does not describe indicators of compromise; sites that ran an affected version on the public internet should be reviewed for unexpected files, users, and scheduled tasks.

**Plugin & theme developers / agencies**
- Audit client sites and managed fleets for Mail Mint and its installed version.
- No API changes are described in the record.

**Hosting & platform teams**
- Prioritize this in vulnerable-plugin scanning and consider WAF rules for serialized-object payloads in form-submission requests.

## Technical details

The advisory identifies the sink as the `handle_form_submission` function, which deserializes untrusted input supplied through form fields (the title says "Arbitrary Form Fields"). This is CWE-502. An attacker-controlled serialized string is unserialized, producing an arbitrary object. The advisory states that a POP chain is available, which converts the object injection into code execution.

The record does not include the patch diff or the exact code path, so the specifics of the 1.31.1 fix (for example, removing `unserialize()` or restricting `allowed_classes`) are not confirmed here. Generally, the safe pattern is to avoid `unserialize()` on request data, use JSON, or pass `['allowed_classes' => false]`.

## Contribution
