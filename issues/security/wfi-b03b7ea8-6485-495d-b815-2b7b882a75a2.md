## Summary

The Nokri job board theme's `nokri_reset_password()` function validates the password reset token insufficiently. An attacker can submit an empty `token` value, and it matches users whose `sb_password_forget_token` user meta is empty or unset. That lets an unauthenticated attacker reset the password of any such account, including administrators, and take it over. Version 1.6.7 fixes it.

## Impact

- **Site owners running Nokri <= 1.6.6:** Unauthenticated full account takeover, including administrator accounts, is possible. Update to 1.6.7 or later immediately.
- **Post-update review:** Sites that ran a vulnerable version should check for unexpected password changes, new administrator accounts, and unfamiliar plugin/theme installs or file changes. The source record does not describe exploitation indicators, so this is general incident-response practice.
- **Theme developers / agencies:** Anyone with a child theme or custom code that calls or overrides `nokri_reset_password()` should confirm it doesn't reimplement the flawed token comparison.
- **Hosting & platform teams:** Theme-bundled auth flows of this kind are reachable without authentication. If patching is delayed, consider a WAF rule or temporarily blocking the reset endpoint (mitigation suggestion, not from the source).

## Technical details

The source record describes the root cause as insufficient reset token validation in `nokri_reset_password()`. The function compares the attacker-supplied `token` parameter against the `sb_password_forget_token` user meta value. When the submitted token is empty and the stored meta is empty or unset (the state for any user who has never requested a reset), the comparison succeeds. The password reset then proceeds for that user.

This is the classic loose-comparison pattern for reset tokens: an empty string equals a missing value. The record does not include the diff or the patched code, so the exact 1.6.7 fix is not stated. A typical remedy would be to reject empty tokens and require a non-empty stored token before comparing, but that is an inference rather than something confirmed by the record.

No hooks, REST routes, or database schema changes are described. The record does not specify how the vulnerable function is exposed (for example AJAX action or form handler).
