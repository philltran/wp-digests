# WordPress Core <= 7.1 - Authenticated (Contributor+) Insecure Direct Object Reference to Arbitrary Post Overwrite

## Summary

WordPress core has an Insecure Direct Object Reference in `_wp_translate_postdata()`. On the post *create* path, where no `post_ID` is supplied, the function honors a raw `ID` parameter from the request. `wp_insert_post()` then treats that request as an update to the existing post with that ID. The per-post `edit_post` capability checks run only on the update path, so they are skipped. As a result, any authenticated user with Contributor-level access or above can overwrite the content of arbitrary existing posts, including posts written by Editors and Administrators.

## Impact

- **Site owners:** Any site with untrusted or semi-trusted accounts at Contributor level or higher is exposed. This includes multi-author blogs, membership sites, and sites that allow open contributor registration. A Contributor could replace the content of any post. **Update core to a patched release on your branch.**
- **Hosting & platform teams:** The fix is backported across every supported branch back to 6.6. Make sure auto-updates for minor releases are enabled, or push the patched minors fleet-wide. Pinned or locked installs need a manual bump.
- **Plugin & theme developers:** If your code passes request data into `wp_insert_post()` or its post-data translation helpers, check whether a caller-supplied `ID` can turn an insert into an update without an `edit_post` check against that specific post. The same pattern of creating a post while trusting a raw `ID` can reproduce this class of bug in custom code.
- **Until patched:** Audit Contributor+ accounts and look at post revisions for unexpected edits by low-privileged users.

## Technical details

According to the advisory, the flaw is a mismatch between which code path runs the authorization checks and which code path does the write:

- `_wp_translate_postdata()` handles two cases. If a `post_ID` is present, it runs the per-post `edit_post` capability checks. If `post_ID` is absent, it treats the request as a new post.
- On the create path, a raw `ID` field in the submitted data was still passed through to the post data array.
- `wp_insert_post()` sees a non-empty `ID` and performs an **update** of that existing post. The target-specific `edit_post` check never ran, because the request came in through the create branch.

The net effect is that an authorization check keyed on `post_ID` could be bypassed with a different user-controlled key (`ID`). This is the CWE-639 pattern. The advisory does not publish the patch diff. Presumably the fixed releases stop honoring `ID` on the create path or apply the `edit_post` check to it, but the advisory does not confirm how the fix works.
