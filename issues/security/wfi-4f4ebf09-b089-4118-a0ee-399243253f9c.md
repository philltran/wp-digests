# TranslatePress – Multilingual <= 3.3.1 - Unauthenticated Account Takeover via Password Reset Link Disclosure

- **Source:** Wordfence Intelligence
- **Type:** Vulnerability
- **Published:** 2026-08-25
- **CVE:** [CVE-2026-19632](https://www.cve.org/CVERecord?id=CVE-2026-19632)
- **CVSS:** 9.8 (Critical)
- **CWE:** CWE-640: Weak Password Recovery Mechanism for Forgotten Password
- **Affected:** TranslatePress – Translate Multilingual sites with AI Translation (plugin) <= 3.3.1
- **Patched in:** 3.3.2
- **Researchers:** Yuto Hyakumoto
- **Link:** [https://www.wordfence.com/threat-intel/vulnerabilities/id/4f4ebf09-b089-4118-a0ee-399243253f9c](https://www.wordfence.com/threat-intel/vulnerabilities/id/4f4ebf09-b089-4118-a0ee-399243253f9c)
- **Usefulness:** 5/5

## Summary

TranslatePress – Multilingual <= 3.3.1 exposes administrator password-reset URLs to unauthenticated users through the `trp_get_translations_regular` AJAX action. When a reset email is generated for an admin whose profile locale is a published secondary language, the URL (including the plaintext reset key and login parameters) is saved as a translatable string in the dictionary table, and the AJAX action can return it. An attacker can use it to take over the administrator account. Version 3.3.2 fixes the issue.

## Impact

- **Site owners:**
  - Update to TranslatePress 3.3.2 or later immediately. The CVSS score is 9.8 and no authentication is required.
  - Exposure requires two conditions: automatic string saving is enabled (the default), and the target administrator's profile locale is a published secondary language. Sites with English-only admins on a default-language setup are less likely to be exposed, but the default configuration satisfies the first condition.
  - Sites that may have been exposed should be reviewed for signs of compromise: unexpected password resets, new administrator accounts, and unfamiliar plugin or theme installs.
  - Consider whether reset URLs may still sit in the translation dictionary tables. The advisory says they are persisted there, but it does not describe whether the patch purges existing rows. Do not assume old rows were removed.
- **Plugin & theme developers / agencies:** Audit client sites running TranslatePress for version and for admin profile locales. Check whether any custom code or logging touches translation dictionary tables.
- **Hosting & platform teams:** Unauthenticated requests to `admin-ajax.php` with `action=trp_get_translations_regular` are the relevant vector. A WAF rule or log search for that action can help triage, but patching is the real fix.
- **Headless & REST consumers:** The advisory names only the AJAX action, not any REST route.

## Technical details

The advisory's description (no diff or patch is included in the source) gives this chain:

1. Automatic string saving (enabled by default) records strings rendered in a translated context into TranslatePress's per-language dictionary tables.
2. When the target administrator's profile locale is a published secondary language, the password-reset message is treated as translatable content. The raw reset URL, containing the plaintext key and login parameters, is therefore persisted as a string in that language's dictionary table.
3. The `trp_get_translations_regular` AJAX action can be called without authentication and returns dictionary entries. An attacker can retrieve the stored reset URL and use it to set a new administrator password.

The weakness is classified as CWE-640 (Weak Password Recovery Mechanism for Forgotten Password). The fixed version is 3.3.2. The advisory does not describe how the patch works, whether by excluding reset emails from string capture, adding authorization or nonce checks to the AJAX action, or something else, so I am not stating one.
