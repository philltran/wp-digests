# Give Tributes <= 2.3.1 - Unauthenticated PHP Object Injection via 'give_tributes_ecard_notify[recipient][personalized][]' Parameter

- **CVSS:** 9.8 (Critical)

- **Patched in:** 2.3.1.1

- **Usefulness:** 4/5

## Summary

The Give Tributes plugin (an add-on for GiveWP) deserializes untrusted input from the `give_tributes_ecard_notify[recipient][personalized][]` request parameter in versions up to and including 2.3.1, allowing unauthenticated PHP Object Injection. The plugin itself ships no known POP chain, so impact depends on another installed plugin or theme providing one. Version 2.3.1.1 patches the issue.

## Impact

**Site owners**
- Update Give Tributes to 2.3.1.1 or later.
- Exposure is conditional. Both of the following must be true: the donation form has **Allow Multiple Recipients** enabled, and the eCard **Custom Message** option is disabled (the plugin default).
- With no POP chain on the site, there is no direct impact. If another plugin or theme provides a POP chain, the outcome could range from arbitrary file deletion and sensitive data disclosure to code execution, depending on that chain.

**Plugin & theme developers / agencies**
- Sites running Give Tributes with multi-recipient forms should be audited for other components that expose gadget chains, since those raise the severity of this bug.
- The endpoint is unauthenticated, so patching should not wait on an assessment of whether a chain exists.

**Hosting & platform teams**
- Consider flagging or prioritizing sites with Give Tributes <= 2.3.1 for update.

## Technical details

The record describes the flaw as deserialization of untrusted input (CWE-502) reachable via the `give_tributes_ecard_notify[recipient][personalized][]` parameter. No diff or patch is included in the source, so the exact code change in 2.3.1.1 is not documented here.

The advisory describes the reachability conditions:

- **Multi-recipient path only.** The single-recipient code path applies `sanitize_textarea_field()`, which neutralizes the payload. The multi-recipient path ("Allow Multiple Recipients" enabled) does not, so the value is stored and later deserialized.
- **Custom Message disabled.** When the eCard "Custom Message" option is enabled, the personalized message becomes a required field, and GiveWP's `give_clean()` blanks serialized input during validation. The donation is then rejected before it is stored. With the option disabled (the default), that protection does not apply.

The practical effect is that the default eCard configuration combined with multi-recipient forms allows attacker-controlled serialized data to be stored and unserialized without authentication.
