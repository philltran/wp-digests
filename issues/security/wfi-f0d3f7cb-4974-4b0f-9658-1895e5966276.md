# TrueBooker <= 1.2.6 - Unauthenticated Account Takeover via Insecure Direct Object Reference in 'truebooker_wp_user_id' Parameter

- **Source:** Wordfence Intelligence
- **Type:** Vulnerability
- **Published:** 2026-08-14
- **CVE:** [CVE-2026-16142](https://www.cve.org/CVERecord?id=CVE-2026-16142)
- **CVSS:** 9.8 (Critical)
- **CWE:** CWE-639: Authorization Bypass Through User-Controlled Key
- **Affected:** TrueBooker – Appointment Booking and Scheduler System (plugin) <= 1.2.6
- **Patched in:** 1.2.7
- **Researchers:** Nabil Irawan

- **Usefulness:** 5/5

## Summary

TrueBooker's `add_front_user_update()` AJAX handler is exposed to unauthenticated requests and trusts a caller-supplied `truebooker_wp_user_id` parameter, passing it straight to `wp_update_user()` with no authentication or ownership check. Any anonymous visitor can therefore rewrite the email address on any account on the site, including an administrator's. Once the email is changed, the attacker triggers WordPress's own lost-password flow and receives the reset link at their own inbox, completing a full administrator takeover. Fixed in 1.2.7; everything up to and including 1.2.6 is exploitable.

## Impact

**Site owners running TrueBooker**
- Treat this as an active-compromise scenario, not a routine patch. Exploitation requires no account, no nonce the attacker can't obtain from a public page, and leaves behind only an email change and a password reset — both of which look mundane in logs.
- **Update to 1.2.7 immediately.** If the plugin cannot be updated in the next few minutes, deactivate it — the vulnerable handler is registered on `init`/`admin-ajax.php` regardless of whether any booking form is rendered.
- After updating, audit for signs of prior exploitation: unexpected `user_email` values on administrator and editor accounts, `wp_users` rows whose email domain does not match your organisation, recent password-reset activity, unfamiliar administrator accounts, and new/modified plugin or `mu-plugins` files. Force a password reset for all privileged users and rotate any credentials those accounts could reach.

**Hosting & platform teams**
- Worth a fleet-wide scan for the plugin slug at ≤ 1.2.6 and a forced update or WAF rule covering `action=add_front_user_update` POSTs to `admin-ajax.php`.
- Because takeover completes through the *legitimate* password-reset path, reset-email volume is a useful detection signal.

**Plugin & theme developers**
- No API change to consume. The pattern is the lesson: any handler registered via `wp_ajax_nopriv_*` that accepts a user ID must never pass that ID to `wp_update_user()` — the identity for a self-service profile update comes from `get_current_user_id()`, never from the request body.

**Headless & REST consumers**
- Unaffected directly; the vulnerable entry point is `admin-ajax.php`, not the REST API. But an account taken over this way grants full REST access with administrator capabilities.

## Technical details

The defect is a textbook IDOR (CWE-639: Authorization Bypass Through User-Controlled Key). TrueBooker registers `add_front_user_update()` as an AJAX callback available to logged-out visitors — i.e. bound on the `wp_ajax_nopriv_` side as well as `wp_ajax_` — so `admin-ajax.php` will dispatch it for a request carrying no cookies at all. Inside the handler, the `truebooker_wp_user_id` request parameter is used verbatim as the `ID` passed to `wp_update_user()`, alongside an attacker-supplied email address.

The handler performs neither of the two checks this operation requires: an authentication check (`is_user_logged_in()` / a capability check such as `current_user_can( 'edit_user', $user_id )`), and an ownership check binding the submitted ID to the session. `wp_update_user()` itself is not an authorization boundary — it is a low-level data-layer function that will happily update whatever `ID` it is given, which is exactly why callers are responsible for the capability check.

Roughly, the vulnerable shape:

```php
// Before (<= 1.2.6) — reachable unauthenticated, ID taken from the request
function add_front_user_update() {
    $user_id = $_POST['truebooker_wp_user_id'];
    wp_update_user( array(
        'ID'         => $user_id,
        'user_email' => $_POST['user_email'],
        // ...
    ) );
}
```

The correct shape derives the identity from the session and gates on capability:

```php
// After — identity from the session, not the request
function add_front_user_update() {
    check_ajax_referer( 'truebooker_front_user_update' );

    $user_id = get_current_user_id();
    if ( ! $user_id ) {
        wp_send_json_error( null, 403 );
    }

    wp_update_user( array(
        'ID'         => $user_id,
        'user_email' => sanitize_email( wp_unslash( $_POST['user_email'] ) ),
    ) );
}
```

The escalation chain is what pushes this to CVSS 9.8: changing `user_email` on an administrator does not by itself yield a session, but WordPress's built-in `retrieve_password()` flow will then deliver a valid reset key to the new — attacker-controlled — address, converting an unauthenticated write into full administrator authentication. No DB schema, hook, or option changes are involved; the fix is purely an access-control correction in the handler.
