# Frontend Admin by DynamiApps <= 3.29.9 - Unauthenticated Privilege Escalation via 'item_id' Parameter

- **Usefulness:** 5/5

## Summary

The plugin's user-update AJAX flow could be abused to bypass a capability check and take over the default administrator account. The bypass occurred when a non-numeric `item_id` value caused the `edit_user` check to be skipped, allowing a signed ACF objects payload to be processed with a user ID that WordPress coerced to `1`. The fix closes the authorization gap in the user update path.

## Impact

- **Site owners:** Update the plugin to the patched release and audit administrator accounts for unauthorized password or email changes.
- **Exposure:** Unauthenticated exploitation requires a public-facing frontend user form; otherwise a subscriber-level account was sufficient.
- **Plugin and theme developers:** If extending the plugin's user-update endpoint, validate `item_id` and ensure capability checks are not skipped for non-numeric identifiers.
- **No action required** for sites that do not use the plugin.

## Technical details

The advisory describes the root cause in the user-update authorization path:

- The unauthenticated endpoint `wp_ajax_nopriv_frontend_admin/forms/change_form` accepted an unvalidated `item_id` parameter.
- `ActionUser::conditions_logic()` gated `current_user_can('edit_user', $user_id)` behind an `is_numeric()` test.
- A crafted non-numeric value such as `1one` caused the capability check to be skipped.
- The attacker could obtain a server-signed `_acf_objects` payload carrying that non-numeric user ID, which WordPress later coerced to integer `1`, the default administrator account, enabling password or email overwrite.

Vulnerable pattern described by the advisory:

```php
if ( is_numeric( $user_id ) ) {
    current_user_can( 'edit_user', $user_id );
}
```

The patched release addresses the bypass; the advisory does not include the exact code change.
