## Summary

ACPT (Premium) through 2.0.66 lets unauthenticated visitors take over any WordPress account, including administrators. The `submit()` function accepts a client-supplied target user ID (via the `acpt_form_post_id` parameter) and passes it to `wp_update_user()` without an authorization check. An attacker can overwrite the victim's email address and password. Version 2.0.67 fixes it.

## Impact

**Site owners**
- Sites running ACPT (Premium) <= 2.0.66 should update to 2.0.67 or later.
- Exploitation requires a public ACPT user form that permits anonymous submissions. Sites without such a form are not exposed through this path, but check your form configuration rather than assuming.
- Successful exploitation means full account takeover, up to administrator. If you ran a vulnerable version with an anonymous user form, audit for unexpected changes to user emails and passwords, and for new or altered administrator accounts.

**Plugin & theme developers / agencies**
- Inventory client sites for ACPT Premium and its version, and check whether any ACPT user form allows anonymous submission.
- No API removals or deprecations are reported. The fix is a version update.

**Hosting & platform**
- CVSS 9.8 with no authentication required; consider WAF rules or virtual patching on requests carrying `acpt_form_post_id` until sites are updated. The record does not describe a specific request pattern beyond that parameter.

## Technical details

The advisory attributes the flaw to missing authorization in the plugin's `submit()` function. For ACPT user forms, the handler lets the submitted request control the target user ID, reportedly through the `acpt_form_post_id` parameter, and then calls `wp_update_user()` with that ID. No check confirms that the requester is authenticated or is permitted to edit that user.

Because `wp_update_user()` updates `user_email` and `user_pass` for whatever ID it receives, an attacker can set the email and password of an arbitrary user. A password reset or direct login then follows.

The record does not include a diff or describe the exact fix in 2.0.67. A typical remediation would bind the target to the current user or enforce a capability check, but that is not confirmed by the source, so verify against the patched release if you need specifics.
