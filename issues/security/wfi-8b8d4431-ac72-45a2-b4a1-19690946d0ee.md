# WordPress Core <= 7.1 - Authenticated (Author+) Missing Authorization to Comment/Note Reparenting via REST API

## Summary

WordPress core's REST comments controller did not check authorization against the **target** post when a comment's or note's parent post was changed. `update_item_permissions_check()` checked only the post the comment was currently attached to. A user who can edit a comment, such as an Author editing a comment on their own post, could move that comment or note onto any other post, including posts they can neither read nor edit. The patched releases fix this missing authorization check (CWE-862).

## Impact

- **Site owners / hosting & platform:** Update to a patched release on your branch. Exploitation needs an authenticated account that can edit at least one comment (Author role or higher), so the risk is highest on multi-author and editorial sites, membership sites, and platforms that hand out Author-level accounts broadly.
- **Editorial workflows using notes:** Notes go through the same controller path and are affected in the same way. A note could be reattached to a post outside the user's permissions.
- **Plugin & theme developers:** Plugins that call the REST comments endpoints to move comments between posts may start getting permission errors after the fix. This happens when the acting user lacks the required capability on the destination post. Review any code that reassigns a comment's post through REST under a low-privilege user.
- **Headless & REST consumers:** Clients that update a comment's parent post through the REST API now also need authorization on the new post. No other API change is described.
- **Action required:** Upgrade core. The record describes no configuration change or migration.

## Technical details

The flaw is in `update_item_permissions_check()` of the REST comments controller (`WP_REST_Comments_Controller`).

- **Before:** When an update request changed the comment's parent post, the permission check ran only against the comment's **current** post. Having edit rights on the existing comment was enough to reassign it anywhere.
- **After (per the advisory):** The **target** post supplied in the update is also authorized, so a comment or note can no longer be moved onto a post the user cannot access.

The advisory covers both regular comments and notes, since both go through this controller. It gives no patch diff, and it names no new hooks, filters, or schema changes.
