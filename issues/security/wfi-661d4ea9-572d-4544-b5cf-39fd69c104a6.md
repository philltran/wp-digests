## Summary

The SMS Alert plugin (≤ 3.9.7) contained a critical authentication bypass that allowed unauthenticated attackers to take over any existing WordPress account by exploiting the `billing_phone` parameter during registration. The vulnerability stemmed from `processRegistration()` setting a session flag (`$_SESSION['sa_mobile_verified']`) upon OTP validation without binding it to the verified phone number, allowing an attacker to verify their own number and then swap in a victim's phone to trigger `wp_set_auth_cookie()` for the victim's account. This issue has been resolved in version 3.9.8 by properly binding the verification state to the specific phone number and validating it before issuing authentication cookies.

## Impact

- **Site owners & plugin administrators:** All installations running SMS Alert ≤ 3.9.7 are vulnerable to full account takeover, including administrator accounts. Update to 3.9.8 immediately.
- **Hosting & platform teams:** No configuration changes or migration steps are required; patching the plugin resolves the issue. Ensure automated update policies cover this plugin.
- **Headless & REST consumers:** No direct impact, as the flaw resides entirely in the plugin's registration/OTP flow and does not affect public REST endpoints or block APIs.

## Technical details

The vulnerability originated in the plugin's registration handler where `processRegistration()` evaluated `$_SESSION['sa_mobile_verified']` as a standalone boolean gate before calling `wp_set_auth_cookie()`. Because the session flag was set to `true` after any successful OTP validation without being tied to the verified phone number, an attacker could verify their own number, then submit a registration payload with a victim's `billing_phone` to hijack the session. The patch in 3.9.8 binds the verification state to the specific phone number, validates that the OTP challenge matches the submitted `billing_phone`, and prevents `wp_set_auth_cookie()` from executing unless the session state and phone parameter are logically aligned. No new public APIs, hooks, filters, or REST routes are introduced; this is a strict security patch to the existing registration logic.
