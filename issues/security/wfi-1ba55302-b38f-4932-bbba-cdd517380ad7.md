# WordPress Core 6.9 -  7.0.1 - Remote Code Execution via REST API Batch Request Route Confusion

- **Source:** Wordfence Intelligence
- **Type:** Vulnerability
- **Published:** 2026-07-17
- **CVE:** [CVE-2026-63030](https://www.cve.org/CVERecord?id=CVE-2026-63030)
- **CVSS:** 9.8 (Critical)
- **CWE:** CWE-670: Always-Incorrect Control Flow Implementation
- **Affected:** WordPress (core) >= 6.9 and < 6.9.5; >= 7.0 and < 7.0.2
- **Patched in:** 6.9.5, 7.0.2
- **Researchers:** Adam Kues

- **Usefulness:** 5/5

## Summary

A critical vulnerability in WordPress core's REST API batch endpoint (`/wp-json/batch/v1`) lets an attacker submit a sub-request that passes validation for one route but gets dispatched to a different, unintended callback. This route/validation desynchronization bypasses the `allow_batch` restriction that is supposed to limit which routes can be invoked through batching, and it also skips the target route's own argument sanitization, so attacker-controlled parameters reach internal callbacks unsanitized. Chained with a SQL injection primitive reachable through the mis-dispatched callback, the flaw allows full remote code execution on affected sites without authentication. It affects all WordPress core installs from 6.9 up to 7.0.1.

## Impact

- **Site owners:** Unauthenticated, critical-severity (CVSS 9.8) RCE against core itself — update to 6.9.5 or 7.0.2 immediately; this is not a plugin issue and cannot be mitigated by disabling third-party extensions.
- **Plugin/theme developers:** Any REST route that sets `allow_batch => false` (or otherwise assumes it cannot be reached through the batch endpoint) may have had that restriction bypassed; routes that rely on the REST API's argument sanitization/validation layer as their only input-safety barrier were similarly exposed via mis-dispatched batch sub-requests. Worth re-auditing custom routes for defense-in-depth validation inside the callback itself, not just in `args` schema.
- **Hosting/platform teams:** Patch fleet-wide to 6.9.5/7.0.2; if immediate patching isn't possible, consider blocking or rate-limiting POST requests to `/wp-json/batch/v1` at the edge/WAF as a stopgap.
- **Headless/REST consumers:** No batch API signature or route was removed — legitimate batch requests continue to work the same way post-patch; no client-side changes required.

## Technical details

The REST API's batch endpoint accepts multiple sub-requests and validates each against its declared route before dispatching. The bug is a desynchronization between the route used for validation and the route actually used for dispatch: a sub-request can be validated against one route (satisfying that route's permission and `allow_batch` checks) but then routed to execute a different callback. Because the executed callback is not the one that was validated, the `allow_batch` restriction on the real target is never consulted, and the target route's own input sanitization/validation is skipped entirely — attacker-supplied parameters flow straight into the callback. This is classified as CWE-670 (Always-Incorrect Control Flow Implementation). The advisory states this confusion can be chained with a SQL injection vector reachable through the mis-dispatched callback, escalating from arbitrary unsanitized input to full remote code execution. No corrected code sample or diff is included in this record.
