# Online Scheduling and Appointment Booking System <= 28.2 - Insecure Direct Object Reference to Unauthenticated Arbitrary Booking Token Disclosure and Deletion via 'order_id' Parameter

## Summary

Bookly <= 28.2 has an unauthenticated IDOR in its booking-flow AJAX handlers. `bookly_get_form_id` stores an attacker-supplied `order_id` from `form_data` into a fresh booking session without checking that the session created that order. `bookly_render_complete` then trusts it and returns the Order's secret token. With that token, attackers can pull appointment data via `bookly_add_to_calendar` and permanently delete non-completed bookings via `bookly_rollback_order`. The issue is fixed in 28.3.

## Impact

**Site owners**
- Any site running Bookly <= 28.2 is exposed to unauthenticated attackers; no account or login is required.
- Sequential order IDs can be enumerated to disclose other customers' order tokens and appointment/calendar information.
- Non-completed bookings can be permanently deleted, which cascade-deletes the `customer_appointment` rows and, when no other customers are attached, the underlying appointment. This is data loss and can disrupt scheduling.
- **Action:** update Bookly to 28.3 or later. Consider reviewing bookings for unexpected deletions, since deleted records may need restoring from backup.

**Plugin & theme developers / agencies**
- Audit client sites for the Bookly version and patch promptly. Anything that integrates with Bookly's booking flow or these AJAX actions should be retested on 28.3.

**Hosting & platform**
- Requests to `admin-ajax.php` with `action` set to `bookly_get_form_id`, `bookly_render_complete`, `bookly_add_to_calendar` or `bookly_rollback_order` carrying an `order_id` are the relevant traffic pattern for detection or WAF rules. The record does not describe the patch's mechanics, so do not treat this as a complete signature.

**Headless & REST consumers**
- No REST routes are named in the advisory; the affected surface is the AJAX actions.

## Technical details

The advisory describes a chain across four AJAX actions (the patch diff is not included, so the exact fix is not described):

1. `bookly_get_form_id` takes the `order_id` from the submitted `form_data` and stores it, unvalidated, in a newly created booking session.
2. `bookly_render_complete` trusts the session-stored `order_id`, looks up the corresponding Order, and returns its secret token. It does not verify that the current session created that order.
3. `bookly_add_to_calendar` can then be used to retrieve calendar/appointment information for the targeted order.
4. `bookly_rollback_order` permanently deletes arbitrary non-completed bookings. The deletion cascades to `customer_appointment` and, when no other customers are attached, to the underlying appointment.

Because order IDs are sequential, they are trivially enumerable. The root cause is classified as CWE-639 (authorization bypass through a user-controlled key): the session's order ownership is never checked against the client-supplied identifier. Version 28.3 is the first patched release.
