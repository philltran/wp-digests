## Summary

Fixes a race condition in single-page WordPress admin apps generated by `@wordpress/wp-build` where Chrome could evaluate a `modulepreload`-ed `@wordpress/boot` before its classic-script dependencies finished executing. On fast CDN-fronted hosts this produced an uncaught `"Cannot unlock an undefined object"` error because `wp.theme.privateApis` (provided by the classic `wp-private-apis` script) was not yet defined when the boot module ran. The fix wraps the dynamic `import("@wordpress/boot")` call in a `DOMContentLoaded` guard, ensuring all classic dependencies have parsed and executed before the boot module evaluates.

## Technical details

The change is entirely in `packages/wp-build/templates/page-wp-admin.php.template`, inside the `{{PREFIX}}_{{PAGE_SLUG_UNDERSCORE}}_wp_admin_enqueue_scripts()` function.

The inline script registered via `wp_add_inline_script()` on the `{{PAGE_SLUG}}-wp-admin-prerequisites` handle changes from an unconditional dynamic import to an IIFE with a `document.readyState` guard.

**Before:**
```js
import("@wordpress/boot").then(mod => mod.initSinglePage({mountId: "...", routes: ...}));
```

**After:**
```js
( ( mountId, routes ) => {
    const run = async () => {
        const mod = await import( "@wordpress/boot" );
        mod.initSinglePage( { mountId, routes } );
    };
    if ( document.readyState === "loading" ) {
        document.addEventListener( "DOMContentLoaded", run );
    } else {
        run();
    }
} )( "{{PAGE_SLUG}}-wp-admin-app", /* routes JSON */ );
```

The PHP side defines the IIFE body in a `$init_js_function` heredoc and assembles the invocation via `sprintf`. A notable secondary change: `mountId` is now passed through `wp_json_encode( '{{PAGE_SLUG}}-wp-admin-app', JSON_HEX_TAG | JSON_UNESCAPED_SLASHES )` rather than being interpolated as a bare string literal, improving XSS safety consistency with the existing `$routes` encoding.

**Root cause detail:** `<link rel="modulepreload">` causes Chrome to fetch, compile, and queue ES modules before the parser reaches subsequent classic `<script>` tags. When `@wordpress/boot` is modulepreloaded, it can start evaluating while classic scripts carrying `wp-private-apis`, `wp-components`, and `wp-theme` are still in the parser queue. `DOMContentLoaded` fires only after all parser-blocking classic scripts have executed, making it the correct synchronization point. The `readyState !== "loading"` fast-path handles the case where the inline script runs after the document has already loaded (e.g., via a deferred or async injection).

`@youknowriad` noted in review that the same `DOMContentLoaded` guard may also be needed for the site editor v2 boot path (`initSiteEditorV2`), but that was not addressed in this PR.
