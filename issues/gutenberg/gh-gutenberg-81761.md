## Summary

The page templates generated by `@wordpress/build` now fall back to the `@wordpress/boot` script module bundled with WordPress Core when the plugin has no local `build/modules/boot/index.min.asset.php`. Previously, a plugin that set `wpPlugin.pages` without shipping its own `packages/boot` got an admin page that enqueued nothing and showed only the "This screen requires JavaScript" notice, with no PHP error. `@wordpress/build` stopped bundling `@wordpress/boot` in 0.20.0, but the templates were never updated to match.

## Impact

**Plugin developers using `@wordpress/build` pages/routes**
- If your plugin defines `wpPlugin.pages` without its own `packages/boot`, pages that rendered blank should work after rebuilding with the fixed `@wordpress/build`. The generated PHP is what changes, so you need to rebuild and ship the new output.
- The fallback path relies on Core shipping the boot module (Core 7.0+ per the README, or the Gutenberg plugin). If neither a local nor a Core asset file exists, the page still enqueues nothing and shows only the JavaScript notice.
- Plugins that already work around this (the discussion cites a `tools/ensure-boot-asset.cjs` script in the WordPress/ai plugin) may be able to drop the workaround.

**Gutenberg / Core builds**
- No change. The local path is checked first and still resolves for builds that compile their own boot package.

**Site owners / hosting**
- No action required.

## Technical details

Both `packages/wp-build/templates/page.php.template` and `page-wp-admin.php.template` are changed the same way. The asset lookup stays plugin-local first, then falls back to Core's path:

```php
// Before
$asset_file = __DIR__ . '/../../modules/boot/index.min.asset.php';
if ( file_exists( $asset_file ) ) { /* enqueue */ }

// After
$asset_file = __DIR__ . '/../../modules/boot/index.min.asset.php';
if ( ! file_exists( $asset_file ) ) {
	$asset_file = ABSPATH . WPINC . '/js/dist/script-modules/boot/index.min.asset.php';
}
if ( file_exists( $asset_file ) ) { /* enqueue */ }
```

The script, module, and style enqueues all sit inside the `file_exists( $asset_file )` block with no else branch, which is why the old miss was silent. The fallback path matches what Core already edits into its generated `wp-includes/build/pages/*/page*.php` copies for 7.0.x.

These templates only read `$asset['dependencies']` and `$asset['version']` to register the `prerequisites` pseudo-module that preloads boot's script dependencies. The actual `@wordpress/boot` ES module is registered separately in `module-registration.php.template`. Core registers it automatically, and a plugin's own registration overrides Core's if present.

The diff also adds a "Boot module" section to the `wp-build` README and a Bug Fixes entry in `CHANGELOG.md`.

## Contribution

@jsnajdr confirmed the fallback logic but noted the cleaner design would be for the page template to call `wp_script_modules()->get_registered( '@wordpress/boot' )` and build the `prerequisites` loader from that. This isn't possible today because script dependencies (`$asset['dependencies']`) aren't part of the registered module data. He proposed a Core enhancement to attach "meta" to `wp_register_script_module`, with this PR still needed for older WP versions. @Mamaduka agreed and the proposal was deferred to a separate issue. @sirreal pointed to related Core Trac tickets #60597 (exposing useful `WP_Script_Modules` methods), #60647, and #61500, and offered to collaborate.
