## Summary

Standalone pages generated by `@wordpress/build` (e.g. `font-library`, `options-connectors`) no longer render for logged-out visitors. The generated `page.php` hooked an interceptor to `admin_init` with no auth or capability check, and `admin-post.php` fires `admin_init` for unauthenticated requests. As a result, `/wp-admin/admin-post.php?page=font-library` returned the page shell, block editor scripts, and REST preload data to anyone. The interceptor now redirects anonymous users to login and returns a 403 for users lacking a per-page capability (default `manage_options`).

## Impact

**Site owners / hosting**
- Anonymous requests to `admin-post.php?page=<slug>` for generated pages now get a 302 to `wp-login.php` instead of a 200 with about 21 KB of editor markup. The linked Core Trac ticket (#66001) tracks the same issue on the Core side.
- Logged-in users without the page's capability now see a 403 `wp_die()` screen.

**Plugin & theme developers using `@wordpress/build`**
- Page configs in `wpPlugin.pages` accept a new optional `capability` string, defaulting to `manage_options`. Any page you already ship that is reachable by a lower-privileged role will now 403 for that role unless you declare a matching capability.
- Set `capability` to whatever you use when registering the page's menu entry, so users who see the menu item don't hit a 403.
- Rebuild to regenerate `page.php`; the fix only takes effect in regenerated output.
- `page-wp-admin.php` output is unchanged, since it renders via `add_menu_page()`/`add_submenu_page()` callbacks that already enforce the menu capability.

**Gutenberg's own pages** now declare: `font-library` → `edit_theme_options`, `site-editor-v2` → `edit_theme_options`, `theme-preview` → `switch_themes`, `media-editor` → `upload_files`. `experiments`, `dashboard`, and `guidelines` use the default.

No REST or block API changes.

## Technical details

**Template (`packages/wp-build/templates/page.php.template`)**: inside `{{PREFIX}}_{{PAGE_SLUG_UNDERSCORE}}_intercept_render()`, after matching `$_GET['page']` and before calling `..._render_page()`, the diff adds:

```php
if ( ! is_user_logged_in() ) {
	auth_redirect();
}

if ( ! current_user_can( '{{CAPABILITY}}' ) ) {
	wp_die(
		__( 'Sorry, you are not allowed to access this page.' ),
		403
	);
}
```

**Build (`packages/wp-build/lib/build.mjs`)**:
- New `DEFAULT_PAGE_CAPABILITY = 'manage_options'`.
- `normalizedPages` now carries `capability` for both string and object page entries, and the value is passed through the page data.
- `generatePagesPhp()` emits a new `{{CAPABILITY}}` replacement (`page.capability || DEFAULT_PAGE_CAPABILITY`).

**Config example**:

```json
{ "id": "font-library", "capability": "edit_theme_options" }
```

**Other files**: `package.json` declares capabilities per page as listed above; `packages/wp-build/README.md` documents the `capability` field; `CHANGELOG.md` gets a Bug Fixes entry; `lib/test/php-generator.js` adds a test asserting the generated interceptor contains `is_user_logged_in()` and `current_user_can( 'edit_theme_options' )`, with the capability check appearing before the render call.

**Caveat**: `{{CAPABILITY}}` is interpolated directly into a single-quoted PHP string with no escaping. CodeRabbit flagged that a capability containing quotes or backslashes could break the generated file or check the wrong permission. The diff does not add escaping, so capability values should be plain identifiers.
